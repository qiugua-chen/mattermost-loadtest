# IM 性能测试方法论：验收标准、核账口径与有效性判定

本文沉淀一套与具体业务无关的 IM 压测方法论，来自一次完整 POC 的方案设计实践。回答三个问题：**测到什么程度算通过（验收标准）、消息怎么数清楚（核账口径）、什么情况下数据作废（有效性判定）**。

> 配套的实测数据样例见 [BENCHMARKS.md](BENCHMARKS.md)；指标的技术口径定义见 [METRICS.md](METRICS.md)。

## 1. 压力模型设计

### 1.1 目标在线数必须有依据

注册用户、在岗用户、日活用户**都不能直接等同于同时在线用户**。缺少生产峰值数据时，采用「目标区间 + 阶梯验证」：设一个上限目标（如 12,000 在线），按 1/3、2/3、全量逐档执行（4,000 → 8,000 → 12,000），每档独立成轮，用实测拐点修正模型。

### 1.2 发送比例与 TPS 推导

| 场景 | 发送比例参考 | 说明 |
|---|---|---|
| 单聊 | 在线用户的 20% 发送，每人固定间隔 | 比例来源于业务经验假设，需在方案评审中确认 |
| 群聊 | 在线用户的 10% 发送 | 群聊有扇出放大，发送比例应低于单聊 |

- **消息 TPS** = 统计窗口内发送成功的**唯一消息数** / 窗口时长；
- **群聊投递量** = 发送成功消息数 × 应收成员数，与发送 TPS **分开统计**，不可混为一个数。

### 1.3 消息正文规范

正文约 1KB，并携带：**Run ID（轮次隔离）、消息序号、发送时间戳**（本项目使用 `send_unix_nano=` 纳秒标记，由 `recordReceiverLatency` 解析，见 [EXT-CHANGES.md](EXT-CHANGES.md)）。缺少这三要素，事后无法做丢失/重复/乱序核账。

## 2. 验收标准矩阵（模板）

| 指标 | 参考红线 | 统计口径 | 属性 |
|---|---|---|---|
| 在线用户数 | 达到目标值，偏差 ≤5% | 稳定阶段有效 WebSocket 连接数 | 硬性 |
| 登录成功率 | ≥99.9% | HTTP、鉴权及连接异常合并计失败 | 硬性 |
| 登录响应时间 | P95 ≤3s（示例，需评审） | 登录接口端到端 | 待评审 |
| 消息发送成功率 | ≥99.9% | 返回成功且取得消息 ID | 硬性 |
| 消息发送响应时间 | P95 ≤1s（示例，需评审） | 发送请求端到端 | 待评审 |
| 在线消息到达率 | 2 秒内 ≥99.9%，最终 100% | 发送时间至接收端首次 WS 事件 | 硬性 |
| 消息正确性 | 丢失 0、业务重复 0、顺序正确 | 按 Run ID + 消息 ID + 序号核账 | 硬性 |
| 离线消息补偿 | 补偿率 100%，重连后 60 秒内补齐 | 断线期间应收数与补齐数对比 | 硬性（本项目暂未覆盖，见 SCENARIOS 未来方向） |

> 用法：「硬性」项任一不达标即整体不通过；「待评审」项的红线数值必须在执行前与业务方书面确认，避免事后争议。

## 3. 消息核账口径（核心）

IM 压测与纯 HTTP 压测的本质区别：消息有**发送、投递、接收**三个时点，必须三方对账。

| 口径 | 定义 |
|---|---|
| 发送成功 | 服务端返回有效消息 ID（不是 HTTP 200 就算） |
| 在线到达 | 接收端**首次**收到对应 WebSocket 事件 |
| 协议重复 | 同一消息 ID 重复接收（WS 层重推） |
| 业务重复 | 同一唯一业务标识产生多个不同消息 ID（重试导致双写） |
| 丢失 | 窗口结束后应收未收（最终到达率 <100%） |
| 乱序 | 同一会话内接收序号与发送序号不一致 |

**关键纪律**：
1. 每轮使用**独立 Run ID**，跨轮数据绝不对账；
2. 协议重复与业务重复**必须分开计数**——前者多为 WS 重连重推（可接受但需记录），后者是发送侧 bug（红线）；
3. 接收样本数远大于发送数（群聊扇出）是**正常现象**，不是重复。

## 4. 结果有效性判定（哪些轮次要作废）

出现以下任一情况，**该轮数据判为无效**，不得进入报告：

- 目标在线数或目标 TPS 未达到（压力没加上去）；
- 脚本或数据错误（账号未注册、频道不存在、参数化失败）；
- 消息采集丢失（接收端日志/CSV 缺失，无法核账）；
- 关键监控缺失（无法证明服务端当时健康）；
- **负载机先饱和**（压测端 CPU/网络先打满，数据反映的是客户端瓶颈）；
- 环境发生未记录的变化（中途改配置、其他任务混入）。

执行前必须完成：版本冻结、账号与群组准备、监控校时（各机时钟同步）、低负载验证、负载机容量试跑。

## 5. 脚本可信度检查清单

正式压测前，逐项确认：

| 检查项 | 最低要求 |
|---|---|
| 参数化与关联 | 账号、Token、channel_id 动态关联，无硬编码 |
| 断言与错误分类 | HTTP 状态、业务码、关键字三层断言，错误分类统计 |
| 连接行为 | WebSocket 长连接保持；超时与重连参数显式配置 |
| 日志与结果 | 按 Run ID 保存发送、接收、错误明细，保留错误样本与关联 ID |
| 低负载验证 | 5~20 用户完成登录、单聊、群聊全链路核账通过，再放大 |

> 本仓库对应实现：`config/users/*.txt` 账号参数化、`LT_LOGIN_*` 登录治理、`receiver-latency.csv` 核账明细、`loadtest-stage-functions.sh` 就绪门控。

## 6. 执行前确认清单（评审用）

- [ ] 目标在线用户数、登录与消息 TPS 目标已评审确认
- [ ] 群聊映射（GM 或频道）与典型群人数已确认
- [ ] 响应时间与到达率红线数值已书面确认
- [ ] 测试版本、环境部署规格、监控清单已冻结并记录
- [ ] 负载机数量、账号分段、统一启动时间已确认
- [ ] 是否执行混合稳定性场景（S04）已确认
