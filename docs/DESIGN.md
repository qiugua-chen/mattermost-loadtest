# 改造设计动机（为什么做这个扩展）

> 本文回答一个问题：上游 `mattermost-load-test-ng` 已经能压测 Mattermost，为什么还要二次开发？
> 逐文件改造清单见 [EXT-CHANGES.md](EXT-CHANGES.md)。

## 1. 上游工具的原始能力

`mattermost-load-test-ng` 是 Mattermost 官方开源压测工具，原始能力包括：

- 按指定用户数启动 `ltagent`。
- 执行登录、发帖、加频道、创建频道等动作。
- 通过 Controller 配置不同用户行为。
- 提供运行期间状态采样。
- 支持 WebSocket 连接和事件统计。

它适合模拟 Mattermost 用户的**活跃行为**，但默认动作偏**通用随机模型**，不完全满足工程化性能测试"明确场景、明确指标、明确验收口径"的要求。

## 2. 实战中遇到的六个问题

| # | 问题 | 影响 |
| --- | --- | --- |
| 1 | Direct 单聊使用随机用户或随机频道 | 无法稳定形成一对一压测模型，结果不可复现 |
| 2 | 通用 `CreatePost` 依赖 team/channel store | 预置账号场景下容易报 `memstore: team store is empty` |
| 3 | GM 群组消息和频道大群未区分 | 两类场景压力模型完全不同，混用导致结论失真 |
| 4 | 登录与正式发消息混在一起 | 登录慢会污染消息接口的响应时间统计 |
| 5 | 只看 HTTP 发消息响应时间 | 无法证明接收端是否及时收到消息（IM 的核心体验） |
| 6 | 原始统计粒度不足 | 难以按接口区分登录、发消息、初始化请求 |

## 3. 改造目标

针对上述问题，本扩展版的设计目标是：

- **场景行为稳定、可复现、可核账**——确定性配对/分组替代随机模型。
- **阶段分离**——登录预热、初始化、正式业务窗口、排空阶段各自独立计时：
  | 阶段 | 内容 | 是否进入核心消息指标 |
  | --- | --- | --- |
  | 登录预热 | 用户登录、session 建立、WebSocket 建连 | 否 |
  | 初始化 | 创建/打开 Direct、GM 或确认频道 | 否 |
  | 正式窗口 | 只执行发消息动作 | 是 |
  | 排空阶段 | 等待 WebSocket 事件到达 | 辅助 |
- **场景细分**——Direct 单聊、GM 群组消息、频道大群各自有专用 action 与压力模型。
- **补齐接收侧证据**——通过消息内嵌 `send_unix_nano` 时间戳 + WebSocket posted 事件，度量端到端接收延迟。
- **保留完整 HTTP 证据**——经本机 Nginx 代理采集全量请求明细。
- **输出可直接进入性能报告的汇总数据**——统一的指标口径（见 [METRICS.md](METRICS.md)）。

## 4. 设计约束

- **不 fork 重写**：全部改造以最小侵入方式落在 simplecontroller 与指标层，保持与上游合并的能力。
- **参数化优先**：地址、账号、频道、配比、间隔全部走环境变量或配置文件，代码零硬编码。
- **证据链完整**：每一轮压测都必须能回答"发了多少、成了多少、对方收到没有、多快收到"。
